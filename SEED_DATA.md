# Seed Data

Phase 5 introduces a small local seed dataset so pfseeker can validate real public gallery architecture before D1 persistence and production Cloudinary inventory exist.

## Why It Exists

The seed dataset lets the project verify:

- crawlable gallery HTML
- category routes
- search behavior
- truthful sorting
- responsive image descriptors
- card rhythm and image proportions
- accessibility basics

It is not production content and does not include fake creator accounts, download counts, popularity rankings, user IDs, or transformed Cloudinary URLs.

## Location

- Asset records: `src/data/assets.ts`
- Taxonomy records: `src/data/categories.ts`
- Filtering, sorting, route helpers, image descriptors, and seed validation: `src/data/discovery.ts`
- Search/filter parsing, canonical URLs, filter pipeline, color-family mapping, and taxonomy validation: `src/lib/search.ts`
- Generated local development media endpoint: `src/pages/seed-media/[id].svg.ts`

## Schema

Each seed asset stores durable metadata only:

- `id`
- `slug`
- `kind`
- `title`
- `alt`
- `localSource`
- intrinsic `width` and `height`
- original `format`
- `animation`
- category slugs
- tags
- `publishedAt`
- local visual metadata used only by the generated development media endpoint

The seed data intentionally excludes transformed Cloudinary URLs, fake creators, fake download counts, fake rankings, and fake user-owned collection state.

## Validation

`validateSeedData()` checks:

- unique IDs
- unique slugs within each asset kind
- supported asset kinds
- positive dimensions
- non-empty titles and alt text
- valid local development media source references
- category compatibility
- non-empty tags
- valid normalized tags
- no duplicate normalized tags per asset
- every category exists and is used by current seed assets
- parseable published dates
- supported formats
- valid local palette metadata

`assertValidSeedData()` runs during module import so invalid seed data fails tests, type checks that import the module, and builds clearly.

## Media Strategy

No real pfseeker Cloudinary public IDs are currently present in the project. Phase 5 therefore uses deterministic local SVG media generated by the project from seed metadata.

This strategy is isolated to development seed content:

- local sources use `/seed-media/{asset-id}.svg`
- SVGs are generated by `src/pages/seed-media/[id].svg.ts`
- each record has original color and motif metadata
- gallery components consume centralized media helpers through `buildSeedImageDescriptor()`
- no remote placeholder service is used
- no assessed reference images, public IDs, titles, metadata, or visual identity are used

The generated media is intentionally more useful than generic gray boxes because it exercises crop behavior, banner proportions, icon fit behavior, image loading, metadata hierarchy, and responsive card layout.

## Search and Filtering

Phase 8 uses the seed dataset for server-rendered filtering across:

- free-text terms
- asset type
- compatible category
- exact normalized tag
- format
- animation state
- orientation derived from dimensions
- color family derived from palette metadata
- truthful sort order

Arbitrary `/search` filter combinations are `noindex, follow`. Gallery and valid category pages remain indexable while using canonicalized filter URLs.

## Migration To D1

The seed dataset is shaped for later migration into D1:

- keep stable IDs and slugs
- store public IDs or local source references as durable media references, not transformed URLs
- keep dimensions and format metadata with assets
- map category and tag slugs through relational tables
- add creator IDs, download counts, moderation state, and ownership only when real systems exist

When real Cloudinary inventory becomes available, replace `localSource` with stable Cloudinary public IDs and keep rendering through the centralized media helpers.

## Detail Routes

Every seed asset now maps to exactly one detail route:

- PFP: `/pfp/[slug]`
- Banner: `/banner/[slug]`
- Icon: `/icon/[slug]`

Route helpers validate both asset kind and slug. A known slug under the wrong type returns 404.
